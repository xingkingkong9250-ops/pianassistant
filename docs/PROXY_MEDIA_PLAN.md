# 代理媒体（Proxy Media）方案评估 —— 拉片助手

> 版本：v1.7.5 现状基线 · 日期：2026-10-25 · 状态：**已实施（v1.11.0 基础功能 / v1.12.0 分段并行提速）**
> 目的：评估「转代理」思路的可行性、风险与成本，与「消除残余阻塞调用」方案对比，供决策。

---

## 一、问题现状

v1.7.3 ~ v1.7.5 已把倍速 / 暂停 / 音轨 / seek 的原生调用全部下沉到后台控制线程，
但用户实测仍出现卡死，且集中在 **大文件 + 反复播放/倍速/快进后退** 组合操作下。

## 二、本次诊断新发现（v1.7.5 代码复查）

### 2.1 硬件解码已开启
`VideoPlaybackService` 构造中已设置 `EnableHardwareDecoding = true`，
**不存在「忘记开硬解」的问题**。因此卡死不是硬解缺失导致的。

### 2.2 仍存在 UI 线程直读 VLC 的阻塞调用（关键）

LibVLC 3 的 `libvlc_media_player_get_time` 内部走 `input_Control(INPUT_GET_TIME)`，
是一次**跨线程同步往返**：UI 线程发请求 → 等 input 线程响应。
当大文件高码率解码繁忙（尤其高倍速重缓冲）时，input 线程迟迟不响应，
UI 线程就被卡住。当前代码仍在 UI 线程调用它的位置：

| 位置 | 调用 | 触发场景 |
|---|---|---|
| `VideoPlaybackService.Position` getter | `_mediaPlayer.Time` | **每次按 ←/→**（`SeekRelative` 读基准位置）、截图、打入/出点、时间轴刷新 |
| `VideoPlaybackService.SeekRelative` | `_mediaPlayer.Time` | 长按 ←/→ 每 50ms 一次 |
| `Volume` getter/setter | `_mediaPlayer.Volume` | 拖动音量滑块（次要） |

**结论**：v1.7.3/v1.7.4 只把「写」类调用下沉了，「读」类（尤其 `Time`）仍在 UI 线程。
这与「反复快进后退 + 暂定/播放 + 变速更容易卡死」的现象完全吻合——每次按键都会
在 UI 线程等一次 input 线程。

### 2.3 seek 无合并窗口
`ControlLoop` 每次唤醒立即执行一次原生 `Time=` 赋值。长按方向键（50ms 一次）时，
等于每 50ms 向 input 线程投一次 seek，频繁打断解码管线，进一步加剧反压。

## 三、代理媒体方案设计

### 3.1 目标
时间轴浏览、快进后退、倍速、截图预览等「高频交互」操作跑在低码率代理上；
导出、原画截图、最终成片仍走源文件。

### 3.2 预设（建议 3 档）

| 预设 | 分辨率 | 码率 | 编码 | 预估体积（3 小时片源） |
|---|---|---|---|---|
| 轻量 540P | 960×540 | 1.5 Mbps | H.264 + AAC | ≈ 1.9 GB |
| 标准 720P | 1280×720 | 2.5 Mbps | H.264 + AAC | ≈ 3.2 GB |
| 快速 360P | 640×360 | 0.8 Mbps | H.264 + AAC | ≈ 1.0 GB |

生成统一用 ffmpeg：`-c:v libx264 -preset veryfast -crf 26 -vf scale=... -c:a aac -b:a 96k`，
关键帧间隔强制收紧（`-g 25`）——**这一条对 seek 响应速度的影响比降码率更直接**。

### 3.3 流程
1. 打开视频 → 立即用源文件正常起播（不阻塞用户）。
2. 后台队列检测代理是否存在（键：源文件内容哈希 + 预设档位），不存在则开跑。
3. 生成中显示细进度条；可暂停/取消。
4. 生成完成 → 弹出「切换到代理」提示，或按设置自动切换。
5. 切换时保持当前播放位置与倍速（seek 到同一时间码重新起播）。
6. 用户可随时手动「源文件 / 代理」切换（顶栏开关）。

### 3.4 数据与映射
- 代理存放：`{数据目录}\proxy\{contentHash前16位}_{预设}\proxy.mp4`
- 会话记录、截图、裁切点、片段**一律以源文件时间码为准**（代理与源精确到帧对齐时可直接复用）。
- 导出截图/片段：始终调 ffmpeg 读**源文件**（现状已是 ffmpeg 抽帧，不受代理影响）。

## 四、优点

1. **解码负担断崖式下降**：540P/1.5Mbps 相比 4K 原片，解码 CPU 与磁盘带宽降一个数量级，
   高倍速重缓冲概率大幅降低。
2. **seek 更快**：码率低 + 关键帧密，input 线程响应快，反压导致 UI 卡死的窗口变小。
3. **磁盘 IO 友好**：网络盘/机械盘上的大文件场景改善明显。
4. **行业标准做法**：剪辑软件（Premiere、DaVinci、FCP）均用同一思路，用户心智无需教育。
5. 顺带解决「4K 片源在低配机器上根本无法流畅拉片」的硬限制。

## 五、缺点与风险

### 高风险
| 风险 | 说明 | 缓解 |
|---|---|---|
| **首次打开等待成本** | 3 小时 4K 片源生成 540P 代理约 8~20 分钟（取决于 CPU）。用户「打开就想拉片」的核心体验被打断 | 代理生成期间源文件照常播放；仅在大文件/高码率时才建议代理；提供「跳过」 |
| **磁盘占用翻倍** | 代理本身可再占 2~4 GB/片；批量片源累积可达几十 GB | 设置里限制代理缓存总容量，超限按 LRU 清理 |
| **时间码对齐误差** | 若代理重编码后帧数/时长有偏差，裁切点、截图、导出会错位 | 强制 `-vsync 0`/`-fps_mode passthrough` 保持原帧率；用 ffprobe 校验时长一致才允许切换 |
| **功能复杂度扩散** | 「当前操作的是哪个文件」这一状态会渗入播放、截图、导出、会话、UI 展示全链路 | 引入 `MediaSource` 抽象（Source / Proxy 两态），集中收口，禁止散落判断 |

### 中风险
- 代理切换瞬间的播放状态迁移（位置、倍速、音轨、字幕）容易出 bug，需专门回归。
- 用户可能误以为「画质变差了」，需要在 UI 明确标注「【代理】」。
- 与现有「内容哈希还原会话」机制叠加，哈希计算与代理生成的 IO 竞争需要排队。

### 低风险
- 一次性多出 ffmpeg 进程管理、磁盘配额、缓存清理等模块化代码。

## 六、成本估算

| 项目 | 估算 |
|---|---|
| 新增模块 | 代理生成服务、缓存管理、源/代理切换抽象、设置项、UI 状态提示 |
| 代码量 | 约 1200~1800 行（含测试） |
| 里程碑拆分 | M8-A 生成与缓存 → M8-B 播放源切换 → M8-C 导出/截图对齐校验 → M8-D UI 与设置 |
| 回归范围 | 播放、倍速、seek、截图、片段导出、会话还原、字幕/音轨 —— 几乎全量 |

## 七、方案对比

| | A. 消除残余阻塞调用 | B. 代理媒体 | C. A + B |
|---|---|---|---|
| 改动量 | 小（约 100~200 行） | 大（1200~1800 行） | 大 |
| 见效速度 | 快 | 慢 | 中 |
| 解决「UI 卡死」 | **高概率直接解决**（卡的是 UI 线程） | 间接缓解 | 高 |
| 解决「解码跟不上/丢帧」 | 无改善 | 显著改善 | 显著改善 |
| 风险 | 低 | 中高 | 中高 |
| 是否需要用户等待 | 否 | 首次需生成 | 首次需生成 |

**判断**：用户反馈的是「卡死（未响应）」，这本质是 **UI 线程被阻塞**，
A 方案精准命中；B 方案改善的是解码吞吐，对「未响应」是间接帮助。
建议 A 先做（可作为 v1.7.6 补丁版），B 作为可选增强功能随后落地。

## 八、A 方案（建议先做）技术要点

1. 新增 `_cachedTimeMs`（`Interlocked`/`volatile`），在 `TimeChanged` 原生回调里**第一时间**更新
   （早于 marshal 到 UI），`Position` getter 改读缓存，彻底移除 UI 线程的 `get_time`。
2. `SeekRelative` 基准位置改用「未到位的 pending 目标值，否则缓存值」，不再直读原生。
3. `ControlLoop` 增加 seek 合并窗口（建议 80~120ms）：窗口内新 seek 只覆盖目标，不额外下发，
   长按方向键时 input 线程压力降到 1/2~1/3。
4. 音量读写下沉控制线程（或做本地缓存 + 防抖下发）。
5. 新增单测：`SeekRelative` 不再触碰原生 `Time`、合并窗口只下发最后一次。

## 九、待确认决策点（已全部落定）

1. ~~是否先实施 A（v1.7.6 阻塞清零）~~ → **已做**：v1.7.6 起阻塞调用清零，随后 v1.11.0 上代理。
2. 默认档位与触发条件 → **默认 720P**（可选 540P/360P）；触发 = **短边 >1080 或长边 >1920 时弹提示**。
3. 切换策略 → **生成完成自动切换代理**，顶栏 W1-R4-19 可随时手动切回源；用户确认后才开始生成。
4. 缓存上限 → **默认 50 GB，LRU 清理**，设置项可调（0=不限制）。

补充（v1.12.0 实测落地的提速方案）：
- 按时长等分多段（每段 ≥60s）→ 多 ffmpeg 进程并行转码 → concat `-c copy` 无损拼接。
- 性能档位 quiet(1 路)/balanced(2 路)/turbo(4 路)，默认 balanced。
- 实测结论：H.264 4K 并行无收益（NVENC 单编码引擎串行是瓶颈）保持软解；
  HEVC/AV1/VP9 等重解码格式走 NVDEC 硬解（`-hwaccel cuda`），四路并行提速约 **3.5×**。
